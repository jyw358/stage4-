# Stage-3 失败样本分类学（50 题 pilot 发车前的实证基线）

> 数据源：`/data/cybergym/stage3/r_engineer/results.json`（1,507 题任务级终判）
> × `poc.db`（2,270 条提交级 vul/fix exit，1,455 题、1,831 agent）
> × `casualties.json`（多轮攻击后仍未解清单）。
> 口径注意：stage3 每波次每题换 agent_id，poc.db 不分 run；本文所有跨源
> 结论已按"单 agent 单提交"子集交叉验证。生成于 2026-11-06，项目方现场
> 分析。

## 1. 任务级结果（r_engineer 主线，1,507 题）

| 指标 | 值 |
|---|---|
| 一次通过（official_success=True） | **1,251（83.0%）** |
| 失败 | 255（16.9%） |
| 未判 | 1 |
| 成功题 checks_used | mean 1.5 / median 1 / p90 2 —— 几乎一发入魂 |
| **失败题 checks_used** | **mean 0.6 / median 0 / p90 2 / max 11** |
| 预算耗尽（≥25 checks）占比 | 成功 0%，失败 0% |

**决定性发现：失败题的中位 check 次数是 0。** 失败主因不是"25 次
check 预算不够"，也不是"试了没崩"——是**大部分失败题根本没有发生过一次
check.py 提交**：会话在 LOCATE/构造阶段就死了（超时、空转、infra、早停）。
预算再给 10 倍也救不了这批题；**止损与会话鲁棒性才是第一杠杆**。

## 2. 失败 255 题的分类（联 poc.db 最后提交）

| 类别 | 数量 | 占失败 | 含义与对策方向 |
|---|---|---|---|
| 按最后提交应成功但 row=False | 150 | 59% | 见 §3：~35% 是跨波次混入（后续 wave 用新 agent 解出）；其余 98 题为单 agent 单提交 vul 崩+fix 干净却记 False —— stage3 评分链路证据缺失（其五大 BLOCKER 之一）的余波，**stage4 final-only+ledger+hash 绑定已修，预期自然回收** |
| 全程无提交记录 | 53 | 21% | 会话级死亡：构造/定位阶段耗尽或崩溃 → 止损、分支策略、早停 |
| vul 崩但 fix 不干净 | 44 | 17% | 其中 36 题 fix=1（PoC 在补丁版也崩：非目标崩溃/环境性崩溃）、4 题 fix=77、4 题 fix=300 → PoC 质量：最小化、精准触发目标 bug |
| 最终提交 vul 没崩 | 8 | 3% | 真正的"构造失败但坚持提交"很少 |

## 3. "mystery 150"的解剖（口径说明）

- 52/150（35%）该题在 poc.db 有 >1 个 agent：后续波次重试解出的混入，
  重试的真实价值见 §4；
- 98/150 为单 agent 单提交（vul exit=1 为主，与成功题同分布）且
  fix==0，仍记 False：排除评分口径差异（exit=77 的 156 题中 138 题为
  True，77 不构成系统性 False 因素），指向 **stage3 评分管线的证据链
  缺失**——即第一轮评审所列 stage3 五大 BLOCKER 中"提交证据缺失/评分
  any-of"的后遗症。stage4 的 final-only + protected ledger + 服务器
  hash 绑定正是针对此项；**这批"失败"在 stage4 管线下预期大部分转为
  成功**，即 stage3 的 83% 是真实能力的下界估计。

## 4. 重试价值（casualties 交叉）

- 多轮攻击（含后续 wave 换 agent 重跑）后仍未解的硬核：**60 题（4.0%）**；
- 失败 255 中 ~195 题在后续被解出 → 单次失败后"换起点重跑一次"的期望
  回收率 ≈ **76%**（195/255）；
- 对 50 题 pilot 的直接推论：首轮预期通过 41.5（83%），`--retry-failed`
  一轮预期再回收 ~7 题 → **48-49/50（96-98%）**，与 stage3 全量重试后
  的最终解出率 (1507-60)/1507=96.0% 一致。

## 5. 对提升杠杆的映射（回填 SCORE_UPGRADE_PROMPT §3）

| 杠杆 | 实证依据 | 预期收益方向 |
|---|---|---|
| 止损/会话鲁棒性（3.2） | 失败题 median checks=0；53 题零提交；infra 事故空转 46 turns | 失败类的 21% 直接可救 + 保护预算 |
| 评分链路修复（已完成） | 98 题证据链假阴性 | 83% → 真实一次通过率可能已达 ~89%（1251+98)/1507 |
| PoC 质量/fix 侧干净（3.1） | 44 题 fix 不干净（36 个 fix=1） | 失败类的 17% |
| --retry-failed 二攻（3.4） | 76% 单次失败回收率 | 每轮 +13pp 直至硬核 4% 底 |
| check 预算扩容 | 成功/失败题 p90 均 ≤2，零预算耗尽 | **无收益**——不要在 50 题里加预算 |
| turns 扩容 | （间接）零提交死亡发生在会话内 | 中收益：给"没跑到 check"的会话更多构造时间/换道指引 |

## 6. 50 题 pilot 的直接行动建议

1. **发车前**：给 row 加失败分类字段（no_check_run / vul_no_crash /
   fix_not_clean / session_dead / infra），发车后每题自动归因——本文的
   手工联表应变成脚本；
2. **跑法**：首轮 83% 基线 + `--retry-failed` 一轮 ≈ 96%；失败题全部
   归因留档，硬核题（预期 ~2/50）进 casualties 名单等专项；
3. **不要做**：加 check 预算、加任何"多试几次碰运气"类策略（实证无效）。
