# Stage-3 失败样本分类学（50 题 pilot 发车前的实证基线）

> **v2（r5 复审勘误后修订，2026-11-06）**：本版按提升方案复审的裁决修正
> 三处表述缺陷，证据分级为【代码证实】/【项目方汇总】/【假设】：
>
> 1. **"失败题 checks 中位数=0"降级为观测值**：`.checks` 是 agent 可写
>    工作区里的**本地调用尝试计数**（调用服务器前 +1，含网络失败），非
>    服务器确认提交数；会话死亡/文件丢失时 row 记录默认 0。中位数 0 只
>    能读作"任务行记录的 check 尝试中位数为零"，不能推出"从未尝试提交"。
>    验证需 root 侧四格联表（`.checks` 快照 × 服务器记录 × 账本 × 退出
>    原因）。
> 2. **"98 题评分链路假阴性"降级为未解释矛盾**：单 agent 单提交 vul 崩 +
>    fix 干净 + row False 存在多个竞争性解释（终判早于该提交、agent/run
>    不匹配、成功记录非终判时最后一条、hash 绑定不一致、fix 回填晚于
>    终判、谓词版本差异），在逐条排除前统一称"**未解释的跨源判定不一致
>    样本**"；(1251+98)/1507≈89.5% 仅为条件性上界，"stage4 自然回收"
>    撤销（需同题同代码评分回放验证）。
> 3. **"76% retry 回收率"改称多轮累计回收率**：分子 195 是多轮/跨波次/
>    跨提示词版本的累计解出，不是单轮同管线 retry 的成功概率。E1 的
>    增益只能用单轮回收率 r1 的情景表表达，不预设 r1=76%。
>
> 原 v1 结论中不受影响的部分：83.0% 一次通过率（row 终判口径）、60 题
> casualties、成功题 checks 中位 1/p90≤2、零预算耗尽（该三项同样为
> 观测值口径）。

> 数据源：`/data/cybergym/stage3/r_engineer/results.json`（1,507 题任务级终判）
> × `poc.db`（2,270 条提交级 vul/fix exit，1,455 题、1,831 agent）
> × `casualties.json`（多轮攻击后仍未解清单）。
> 口径注意：stage3 每波次每题换 agent_id，poc.db 不分 run；本文所有跨源
> 结论已按"单 agent 单提交"子集交叉验证。生成于 2026-11-06，项目方现场
> 分析。

## 1. 任务级结果（r_engineer 主线，1,507 题）

| 指标 | 值 |
|---|---|
| 一次通过（official_success=True） | **1,251（83.0%）** |
| 失败 | 255（16.9%） |
| 未判 | 1 |
| 成功题 checks_used | mean 1.5 / median 1 / p90 2 —— 几乎一发入魂 |
| **失败题 checks_used** | **mean 0.6 / median 0 / p90 2 / max 11** |
| 预算耗尽（≥25 checks）占比 | 成功 0%，失败 0% |

**观测（v2 降级表述）：失败题的 row 记录 check 尝试中位数为 0**（注意
`.checks` 是 agent 可写侧的调用尝试计数，丢失默认 0——见顶部勘误 1）。
row 口径下预算耗极为零成立；"失败大头是提交前死亡"降级为**待验证假设**，
需 G2 的 root 侧归因（四格联表）裁决。预算扩容在观测口径内仍无依据。

## 2. 失败 255 题的分类（联 poc.db 最后提交）

|---|---|---|---|

| 最终提交 vul 没崩 | 8 | 3% | 真正的"构造失败但坚持提交"很少 |

## 3. "mystery 150"的解剖（口径说明）

- 52/150（35%）该题在 poc.db 有 >1 个 agent：后续波次重试解出的混入，
  重试的真实价值见 §4；
- 98/150 为单 agent 单提交（vul exit=1 为主，与成功题同分布）且
  fix==0，仍记 False：排除评分口径差异（exit=77 的 156 题中 138 题为
  True，77 不构成系统性 False 因素），指向 **stage3 评分管线的证据链
  缺失**——即第一轮评审所列 stage3 五大 BLOCKER 中"提交证据缺失/评分
  any-of"的后遗症。stage4 的 final-only + protected ledger + 服务器
  hash 绑定正是针对此项；**这批"失败"在 stage4 管线下预期大部分转为
  成功**，即 stage3 的 83% 是真实能力的下界估计。

## 4. 重试价值（casualties 交叉）【v2：口径修正】

- 多轮攻击（含后续 wave 换 agent、换提示词版本）后仍未解的硬核：
  **60 题（4.0%）**【项目方汇总】；
- 失败 255 中 ~195 题在多轮后解出 → **多轮累计回收率 ≈76%**——这**不是**
  单轮同管线 retry 概率 r1（含新 agent 重抽、波次配置差异等混杂）；
- 50 题正确表达（E1 情景表，p0=83% 时一次有效 retry 的期望新增
  = 50×17%×r1）：

| r1 假设 | 新增通过（期望） | 最终通过率 |
|---|---|---|
| 20% | 1.7 | 86.4% |
| 40% | 3.4 | 89.8% |
| 60% | 5.1 | 93.2% |
| 76%（多轮上界，乐观） | 6.5 | 95.9% |

r1 的真实值由 50 题 pilot 的 G3 严格一次有效重试实测得出。

## 6. 50 题 pilot 的直接行动（v2：对齐 r5 发车门槛 G1-G6）

1. **G2 前置**：先上 root 侧可信归因（`.checks`×服务器×账本×退出原因
   四格联表），再谈止损与换道的定量收益；
2. **跑法**：首轮（B4 冻结队列）→ 按评测分层报告"首轮成功率 / 一次有效
   retry 后成功率 / 按题源分层"三个指标；E1 严格一次有效重试实测 r1；
3. **不要做**：加 check 预算；任何"多轮抽签"式重试；在归因可信前把
   E2① 的 25/35 turns 当硬停止线。
