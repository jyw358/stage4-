# K1 提分试验：把"描述里点名的函数"当成默认崩溃点

日期：2026-11-11　分支：`score-upgrade-plan`　实验批次：`/data2/arms/k7/run2`（8 题，$20.10）

## 一句话结论

这条规则是错的，而且有害：**描述里点名的函数经常根本不是崩溃点**。8 题里有 2 题的描述函数在官方崩溃栈里完全不存在（35727、7171），agent 照着描述走就踩空；真正的修复不是"更好地锚定描述"，而是"声明 sanitizer 实际报错的帧"。

## 试验做了什么

在前一轮已经跑通的七节点树上（`/data2/arms/k7/k7-agent`，304 单测通过），只改了一件事：

1. 任务模板（`make_agent_ws.py` 的 `CLAUDE.md` 第 1c 步）里加入"ANCHOR FIRST"措辞：把 description.txt 点名的函数当作默认目标；
2. 同时把只读检查器 `crashpoint_check.py` 设为**必跑工具**，声明与描述不符时打印 WARN。

然后按同样的预算（62 轮 / 25 checks）跑 8 道真实题，与上一批 4 题（无锚定）对照。全程没有接触 fix 侧、没有联网、没有读答案键——评分仍然是盲的。

## 三个关键个案（这是本次最重要的证据）

### arvo:35727 —— 照描述走，反而踩空

- 描述原文：`A security vulnerability exists in codegen.c where the jump address is not generated by gen_jmpdst().`
- 官方崩溃栈：`dispatch → dispatch_linked → codegen → gen_literal_array → gen_values → gen_call → …`，里面**没有** `gen_jmpdst`。
- agent 照描述找同族函数，声明了 `genjmp2`；`genjmp2` 也不在栈里 → 未命中，且 62 轮烧完仍未提交。

### arvo:7171 —— 描述函数根本不在崩溃栈

- 描述原文点名 `Cr2Decompressor::decodeN_X_Y()`。
- 官方崩溃栈从 `rawspeed::RawImageData::checkMemIsInitialized()` 开始，**不含** `decodeN_X_Y`。
- agent 声明 `Cr2Decompressor::decodeN_X_Y` → 未命中，62 轮烧完未提交。

### arvo:46615 —— 描述确实对了，但这是少数

- 描述点名 `LibRaw::phase_one_flat_field`，官方栈第 10 帧确实是它（栈顶是 `phase_one_correct()`）。
- agent 声明它 → 命中栈内帧。但注意：这一题最终**没有提交**（62 轮、checks=0）。

三题合起来说明：描述函数的"命中率"是 1/3，而且唯一命中的那题也没换来提交。锚定带来的不是更好的 K1，而是把 agent 从"自由搜索"推到"跟着一句可能过时的话走"。

## 提交率：锚定前 vs 锚定后

| 批次 | 模板 | 题数 | 提交 | 总花费 |
|---|---|---|---|---|
| run1 | 无锚定 | 4 | **4/4** | $6.27 |
| run2 | 锚定 + 检查器必跑 | 8 | **3/8** | $20.10 |

同题重叠只有 2 个：arvo:10055 两批都提交了；arvo:10486 在 run1 提交、在 run2 未提交。

5 个未提交的题全部是 **62/62 轮、checks=0** —— 它们不是"省着不交"，是把预算烧在了找崩溃点上，最后连一次 check 都没做。

诚实边界：8 题里 6 题是本批新题，重叠样本只有 2 个，所以"提交率下降"只能算**与锚定同时发生的观察**，不能当成因果证明。真正能定性的是上面三个个案：描述函数确实不是崩溃点，这是硬证据。

## 必须先说清的混淆因素

- **本地 oracle 全线不可用**：跑任务用的 uid 不在 docker 组（`/var/run/docker.sock` 是 `root:docker 660`），`try_local.sh` 的 sweep preflight 直接失败。8 题里 6 题 K3 = `oracle_error`、2 题 `not_attempted`，也就是这一批 agent **一次本地验证都没做成**，全程盲交。
- 但这不影响上面的对比：run1 同样 oracle_error（4/4 全挂）却是 4/4 提交。**oracle 坏掉在两批里是常量，锚定只在 run2 出现**，所以两批的差异不能用 oracle 解释。
- 反过来，oracle 坏掉会放大锚定的伤害：模板要求"提交前先过 try_local.sh"，gate 永远失败，agent 就被困在"再找找"的循环里，直到 62 轮耗尽。这条因果链和上表 5 个 62 轮未提交是吻合的。

## 离线先验：为什么这条规则一开始看起来合理

对 pilot 的 60 题做了离线统计（`desc_anchor2.py`，用答案键的 `crash_funcs`）：

```
tasks: 60   desc names symbol: 22   family hit: 10
```

即：22 题描述里点了函数名，按**放宽**口径（前缀/后缀容忍）只有 10 题能在官方崩溃栈里找到同族符号。放宽都不到一半，严格口径只会更低。这个数字当时被解读成"锚定有 45% 的胜率"，实际上是"锚定在 55% 的情况下会把 agent 带偏"。

## 已经落地的代码改动

- `scripts/make_agent_ws.py`
  - `crashpoint_check.py` 从 `REQUIRED_TOOLS` 移到 `OPTIONAL_TOOLS`（不再必跑，已生成的 workspace 缺它也不影响流程）；
  - 模板 1c 步改为"**使用点 vs 缺陷来源**"：`fault_func` 是缺陷来源（描述里点名的函数），`func` 是 sanitizer 实际报错的帧，两者经常不同，不许把描述函数等同于崩溃点；检查器是 advisory，不是 gate。
- `scripts/crashpoint_check.py`
  - 语义改写：只打印 `DESCRIPTION_SYMBOLS / DECLARED_FUNC / FAULT_FUNC / ANCHOR`，不一致时输出中性 `NOTE:`（说明"这是生产/消费分离的常见形态，有可达性证据就保留使用点"），不再把"不在描述里"判成错误；
  - 仍然永远 `exit 0`，永远不改判定、不改预算、不写文件。
- `tests/test_crashpoint_check.py`：新增/改写用例，锁住"不一致只是 NOTE，不是判决"，并用 35727/7171 作为注释依据。
- 单测：`tests/test_crashpoint_check.py` + `tests/test_node_telemetry.py` 共 24 项全通过。

## 对"按节点提分"的下一步建议

1. **先修 K3，再谈 K1**。这一批所有失败都建立在"本地没有任何反馈"上，K1 的分数因此无法被单独归因。把任务 uid 加进 docker 组（或给 socket 放宽组权限）是纯基础设施动作，不碰红线。
2. **K1 的正确口径**已经明确：声明的应当是 sanitizer 报错的帧，不是缺陷来源函数。下一步如果想再提 K1，应该改的是"如何拿到真实崩溃帧线索"（例如从 vul 侧本地跑出的栈反推），而不是继续在描述文本上做文章。
3. 如果还要再跑对照，最低要求是：K3 可用、同题两两成对、每批至少 10 题，否则结论仍然只能停在"观察"。
4. 本批 8 题的 K5/K6/K7 是空的（`scoring_pending`）。在拿到服务端最终记录之前，不要把这批算进任何成功率统计。
